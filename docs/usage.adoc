= Usage
:imagesdir: media/

Follow these steps to start using the ID provider

== OIDC server

You will need access to an OIDC server. These are available from a range of different providers like Google, Entra, Auth0 and ID-porten, and you may run your own based on software.

For your respective provider you will typically need to create a Client or application that will represent the Enonic integration. Typical values you will need later from this setup are typically:

- Client ID
- Client secret
- Issuer Identifier (URL)

== Installation

On your Enonic server, start by installing the application to your Enonic instance. It is https://market.enonic.com/vendors/enonic/oidc-id-provider[available on Enonic Market].

== Configure

Secondly, the application requires a detailed configuration in order to communicate with the 3rd party OIDC server. Create a and tune a configuration file called `com.enonic.app.oidcidprovider.cfg` and add it to your XP instance.

Full details on how to configure the application is described in <<config#configuration, the configuration chapter>>.

You may also find our <<examples#examples, configuration examples>> useful.

NOTE: Your Enonic ID provider should automatically be created once you add your configuration file


=== Manual setup

If you disable `autoInit`, the ID providers may manually be created by following these steps:

. From Enonic admin console: `XP menu` -> `Users` -> `New` -> `ID provider` https://www.youtube.com/watch?v=QZpBdsDlkA0[admin tool "Users"]
. Fill in the `displayName` field, which generates the *ID provider name* just below
+
image:idprovider-name.png[title="ID provider name is found/set in the name field below the displayName", width=500px]
+
The ID provider name cannot be changed later, so choose wisely before saving.
+ 
. For the "Application" field, select the "OIDC ID Provider" app you installed earlier.


== Mapping

Finally, you will need to map the ID provider to an Enonic ingress/vhost where it will be used - i.e. to enable login for the XP admin console, a website or an API.

=== Ingress
When using the self-service cloud, simply edit the Ingress, then select the ID provider you created above i.e. `myoidcprovider`.

Save, and the change should take effect shortly.


=== Vhost
To manually configure the ID provider on your XP instance, you will need a vhost definition.

Edit the XP configuration file `com.enonic.xp.web.vhost.cfg`, and map the id provider to your vhost.

(See https://developer.enonic.com/docs/xp/stable/deployment/vhosts[Virtual Host Configuration] for more information).

.Example vhost mapping for Admin console
[source,properties]
----
mapping.example.host = xp.example.com
mapping.example.source = /
mapping.example.target = /admin
mapping.example.idProvider.myoidcprovider = default
----

NOTE: `myoidcprovider` in the example above must match the name you used in the ID provider configuration.

=== Device login for CLIs and other browserless clients

Enonic XP serves the OAuth device authorization flow (RFC 8628) for this ID provider's users: a client asks XP for a code, the user signs in through this ID provider as usual and approves the code on a verification page, and XP issues its own access and refresh tokens. This app provides the page the user sees; everything else is XP's, configured per virtual host in `com.enonic.xp.web.vhost.cfg`. See https://developer.enonic.com/docs/platform/stable/security/access-tokens[access tokens and device login] in the XP documentation.

Enable the `device`, `code` and `register` flows on the host where users approve, and `autologin` with an `audience` on the host where the tokens are used. The scopes the ID provider declares, see <<config#consent, scopes and clients>>, say what a client may ask for and the roles each scope gives; the token gets the roles of the scopes the user keeps. Without declared scopes, a client asks for none and the token carries the user's full memberships.

.Example: approve on the admin host, use on the API host
[source,properties]
----
mapping.admin.host = xp.example.com
mapping.admin.source = /
mapping.admin.target = /admin
mapping.admin.idProvider.myoidcprovider = default
mapping.admin.idProvider.myoidcprovider.flows = login,logout,device,code,register

mapping.api.host = api.example.com
mapping.api.source = /
mapping.api.target = /
mapping.api.idProvider.myoidcprovider = default
mapping.api.idProvider.myoidcprovider.flows = autologin
mapping.api.audience = api
----

A client obtains its code at `+https://xp.example.com/_/idprovider/myoidcprovider/device/code+` and its tokens at `+.../token+`.

Bearer tokens of your OpenID provider keep working through autologin. With `autoLogin.allowedAudience=@@{vhost.audience}` the host's audience and the ID provider's scopes apply to them too, see <<config#tokens-through-xp, tokens through XP>>.

== Redirect/Callback URI

Finally, if you want to use form-based authenticated (aka Authorization Code Flow), End-Users will be redirected back to your Enonic endpoint from the authorization server. For security reasons you will need to register this URL in the configuration of your OIDC providers Client/Application.

The callback URL depends on your Enonic Vhost/Ingress and the name of the ID Provider you want to use. It typically has the following format: `[host+sourcepath]/_/idprovider/[idprovidername]`, where `idprovidername` must match the ID provider registered in Enonic XP.

Example for a site:: https://www.example.com/_/idprovider/myoidcprovider

Example for admin:: https://www.example.com/admin/_/idprovider/myoidcprovider
